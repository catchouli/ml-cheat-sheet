Position encoding

How a transformer knows the order of its tokens, from the original sine waves to RoPE.

Why it's needed

Attention sees its input as a set: shuffle the tokens and each output just moves with its token. Without extra information, “dog bites man” and “man bites dog” look the same. (The causal mask leaks a little order, but not enough to rely on.)

There are two broad approaches:

  • Absolute: give each position its own vector and add it to the token embedding at the input. Sinusoidal and learned embeddings work like this.
  • Relative: change the attention scores so they depend on the distance between query and key, \(t - j\). RoPE, ALiBi and T5's bias work like this. Most current models use RoPE.

Sinusoidal (2017)

From the original transformer paper (Vaswani et al., Google, “Attention Is All You Need”). Each position \(p\) gets a fixed vector of size \(d\), added to the token embedding:

\[ PE_{(p,\, 2i)} = \sin\!\left( \frac{p}{10000^{2i/d}} \right) \qquad PE_{(p,\, 2i+1)} = \cos\!\left( \frac{p}{10000^{2i/d}} \right) \] \[ x_p = \text{embedding}(\text{token}_p) + PE_p \]

Each pair of dimensions \((2i, 2i+1)\) is a point going round a circle as \(p\) increases, like the hand of a clock, at angular speed \(\omega_i = 10000^{-2i/d}\). The first pair turns 1 radian per position; the last turns about 10000 times slower. Together they work like the digits of a number: fast ones distinguish neighbours, slow ones tell far-apart positions apart.

Why sines and cosines: moving \(k\) positions along rotates each pair by a fixed angle, \(k\omega_i\), whatever \(p\) is. So \(PE_{p+k}\) is a linear function of \(PE_p\), which the authors hoped would make relative positions easy to learn:

\[ \begin{pmatrix} \sin\bigl((p + k)\omega\bigr) \\ \cos\bigl((p + k)\omega\bigr) \end{pmatrix} = \begin{pmatrix} \cos k\omega & \sin k\omega \\ -\sin k\omega & \cos k\omega \end{pmatrix} \begin{pmatrix} \sin p\omega \\ \cos p\omega \end{pmatrix} \]

No parameters, and it's defined for any position, though in practice models don't generalise well past the lengths they were trained on. The paper also scales the token embeddings by \(\sqrt{d}\) before adding, so the position signal doesn't drown them out.

Learned embeddings

Simpler still: a second embedding table, indexed by position instead of token, learned like any other weight.

\[ x_p = \text{tok\_emb}[\text{token}_p] + \text{pos\_emb}[p] \qquad \text{pos\_emb}: T_{\max} \times C \] 
self.pos_emb = nn.Embedding(block_size, d_model)
x = self.tok_emb(idx) + self.pos_emb(torch.arange(T, device=idx.device))  # (B, T, C), broadcast over B

The original paper tried this too and found it worked about as well as sinusoidal. It's what BERT, GPT-2 and GPT-3 use, and what CatGPT's stage 4 uses. The catch: there's nothing for position \(T_{\max}\) and beyond, so the context length is fixed at training time, and each position is learned separately, so the model has to learn that positions 7 and 8 are neighbours.

Relative biases

Instead of changing the inputs, add a bias to each attention score that depends only on the distance \(t - j\):

\[ S_{tj} = \frac{q_t \cdot k_j}{\sqrt{d}} + b(t - j) \]
MethodBias \(b(t - j)\)Used by
T5 relative biasA learned scalar per head for each distance, with distances grouped into buckets that get wider further away.T5
ALiBiFixed, no parameters: \(-m_h\,(t - j)\), a straight-line penalty on distance with a different slope \(m_h\) per head.BLOOM, MPT

ALiBi in particular extrapolates well to sequences longer than it was trained on, because a longer distance just means a bigger penalty.

RoPE

Rotary position embedding (Su et al., 2021). Used by LLaMA, Mistral, Qwen, Gemma, GPT-NeoX and most current LLMs. Instead of adding anything, rotate each query and key by an angle proportional to its position. It's applied inside every attention layer, to \(q\) and \(k\) only (not \(v\), and not the residual stream).

The rotation

Split the head's \(d\) dimensions into \(d/2\) pairs. Pair \(i\) gets its own frequency, the same spectrum as the sinusoidal encoding:

\[ \theta_i = b^{-2i/d}, \quad i = 0, \dots, \tfrac{d}{2} - 1 \qquad (b = 10000 \text{ usually}) \]

At position \(m\), rotate each pair by the angle \(m\theta_i\), using the 2D rotation matrix:

\[ \begin{pmatrix} x'_{2i} \\ x'_{2i+1} \end{pmatrix} = \begin{pmatrix} \cos m\theta_i & -\sin m\theta_i \\ \sin m\theta_i & \cos m\theta_i \end{pmatrix} \begin{pmatrix} x_{2i} \\ x_{2i+1} \end{pmatrix} \]

Written out without the matrix:

\[ x'_{2i} = x_{2i} \cos m\theta_i - x_{2i+1} \sin m\theta_i \qquad x'_{2i+1} = x_{2i} \sin m\theta_i + x_{2i+1} \cos m\theta_i \]

The whole vector's rotation \(R_m\) is block-diagonal: \(d/2\) independent 2D rotations, each turning at its own speed. Rotations don't change length, so \(\lVert R_m x \rVert = \lVert x \rVert\).

As complex numbers: treat pair \(i\) as \(z_i = x_{2i} + \mathrm{i}\, x_{2i+1}\). Then rotating is just multiplying: \(z'_i = z_i \, e^{\mathrm{i} m \theta_i}\).

Why it's relative

Query at position \(m\), key at position \(n\). Rotating one by \(m\theta\) and the other by \(n\theta\) changes the angle between them by \((n - m)\theta\):

\[ (R_m q)^\top (R_n k) = q^\top R_m^\top R_n\, k = q^\top R_{n - m}\, k \]

since \(R_m^\top = R_{-m}\) (rotating back) and rotations add: \(R_{-m} R_n = R_{n-m}\). The score depends on the two vectors' content and their distance \(n - m\), never on the absolute positions.

Because the fast pairs wrap round quickly and the slow pairs barely move, the model can use fast pairs for “what's nearby” and slow pairs for long-range matching. And unlike learned embeddings, there's no table to run off the end of.

Pairing dimensions

The paper pairs adjacent dimensions, \((x_0, x_1), (x_2, x_3), \dots\). Many implementations (GPT-NeoX, LLaMA in Hugging Face, CatGPT's stage 7 hint) instead pair each dimension with the one half a vector away, \((x_i, x_{i + d/2})\), because it's easier to vectorise:

\[ x' = x \odot \cos + \operatorname{rotate\_half}(x) \odot \sin \qquad \operatorname{rotate\_half}\bigl([x_1;\, x_2]\bigr) = [-x_2;\, x_1] \]

where \(x_1, x_2\) are the two halves of \(x\), and \(\cos\), \(\sin\) hold \(\cos m\theta_i\) and \(\sin m\theta_i\) with the \(d/2\) angles repeated twice (cat([angles, angles])). For each \(i\) that gives \(x'_i = x_i \cos - x_{i+d/2} \sin\) and \(x'_{i+d/2} = x_{i+d/2} \cos + x_i \sin\): the same rotation, on a different choice of pairs.

The two layouts are equally good for training from scratch, since the learned \(W_Q\), \(W_K\) can produce either ordering. But weights trained with one don't work with the other, which is a classic bug when loading someone else's checkpoint.

The rotation is the same for every head, and positions come from the sequence index. With a KV cache, the new queries' positions continue from where the cache ends, not from 0.

Longer contexts

Positions beyond the training length produce angles the slow pairs never saw. Common fixes, all of which stretch the slow frequencies:

MethodIdea
Position interpolationDivide positions by the extension factor, so a longer sequence maps back into the trained range of angles. Needs a little fine-tuning.
Larger baseRaise \(b\) (Llama 3 uses 500,000), so every pair turns more slowly. “NTK-aware” scaling does this by a rule.
YaRNLeaves the fast pairs alone, interpolates the slow ones, and blends in between.

2D RoPE for images

Image patches have a row and a column rather than a single position. The usual (“axial”) 2D RoPE splits each head's dimensions in two: one half is rotated using the patch's row index, the other half using its column index, each with ordinary 1D RoPE. The score then depends on the vertical and horizontal offsets between patches.
